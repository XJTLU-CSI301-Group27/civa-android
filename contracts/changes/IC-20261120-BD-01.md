# BD MVP 接入与显式开源食谱导入

提出时间：2026-11-20 13:48 +08:00。提出组：BD。状态 PROPOSED，不代表 EF 已审批。用户已要求在现有仓库实现 BD、可调整接口并维护交接文档，并进一步明确先做排餐与历史食记 MVP、接入开源食谱、暂缓热量和复杂跨组功能。

## 原因与兼容性

现有 feature-bd 没有页面；所有 planning/records 操作和 AC 菜谱接口为 501。沿用已有 OpenAPI，不增加或修改 HTTP 端点、字段、单位、权限或模型，不手改生成代码。

客户端新增 BdHost 作为应用提供的依赖入口，继承已有 NavHost，方法为 ApiProvider api()、ApiCalls calls()、SessionStore sessions()；由 MainActivity 实现。构造器无参数的 PlanningFragment、DiaryFragment 供 app 导航使用；MealEditorFragment.create(String reference) 和 CookingFragment.create(String reference) 是恢复安全的页面工厂。

MEAL_EDIT reference 为 YYYY-MM-DD 或 YYYY-MM-DD|entry UUID；COOKING_CONFIRM reference 为 recipe UUID|servings|plan slot UUID（末项可空），仅供未来做饭接入。后者不在 MVP 主流程暴露。实体身份最终由服务端验证，不能信任导航参数作权限依据。

## 涉及 AC/EF 的最小适配

- 新 RecipeCatalogController 成为生成 RecipeApi 的唯一路由持有者：只实现已有 listRecipes/getRecipe/listWishlist；新增、编辑、归档和收藏写入继续明确返回 501。AC 接入时扩展或替换该类，不能再增加同一路由 Controller。它只读统一数据库，不建立 BD 私有菜谱副本。
- BdRules、PlanningService 和 RecordsService 使用既有 schema。家庭权限和菜谱引用存在性采用最小只读查询适配。EF 后续提供统一公开访问检查服务时应协调替换，AC 菜谱详情接入不会改变 BD HTTP 调用。
- 追加 V20261120134000__BD_starter_ingredient_dictionary.sql，只补充显式食谱导入需要的标准食材和别名，不改旧迁移、不修改既有映射。请 AC 核对命名、单位和字典归属。已应用后不得更改历史脚本，后续用前向迁移调整。
- scripts/bd_import_recipes.py 是显式开发工具：必须指定现有家庭和活动 OWNER；不自动创建身份或导入到所有家庭。导入同一统一 recipes/recipe_ingredients，固定家庭内 UUID，事务内执行，重复导入保留现有内容。
- 源文本未标准化克数、人数和热量。每道菜以一个计划单位导入，食材线 trackStock=false、quantity=0 仅为未跟踪的契约占位，真实用量仍在原文，禁止用于自动库存扣减或热量推断。MVP 页面展示这一限制。后续由用户或 AC 显式补齐才允许开启跟踪。
